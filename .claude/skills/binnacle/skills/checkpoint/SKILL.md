---
name: checkpoint
description: Close or rotate a Product session. Draft the durable decisions it made into this project's canonical sources, then write and commit them once the human confirms, and record the checkpoint with Binnacle.
disable-model-invocation: true
---

This session is disposable. Whatever it decided that the next session needs must reach the repository before it closes (`docs/workflow/01-product-workflow.md`). Binnacle writes no file (ADR-0020). This session writes and commits them, and only what the human confirms, besides the roadmap's derived part (step 3).

Give the human each command you offer them alone in a fenced block, which copies in one click: a skill such as `/binnacle:daemon start` in a plain fence, a shell command such as `binn daemon start` in a `bash` fence. A file's text you draft, such as the roadmap's `Next action:` paragraph, keeps its command in backticks, as the file writes it.

Speak to the person in the language of this conversation; these instructions stay English. Word every attention item, diagnostic and error from its `code`, `message` and `params`, in that language, with the Task ids, paths and numbers it names, and never show its code: codes are for you. Keep commands, paths, Task ids, branch names, model names, a file's own markers such as `Status: DONE`, and the names Binnacle, Graphify, Obsidian, Serena and the harnesses as written. Mark a value Binnacle calculated with one word in brackets, "(estimate)", and a reading from runs with "(from activity)"; say an unknown value as "no data", never zero. In Russian, the marks are "(оценка)", "(по активности)" and "нет данных", and the terms are: Task — задача; Epic — эпик; Current Epic — текущий эпик; Next action — следующий шаг; Suggested step — предложенный шаг; Product Snapshot — снимок проекта; Product session — продуктовая сессия; Product Steward — продуктовый агент; roadmap — роадмап; Spec — спецификация; Ticket — тикет; Epic brief — бриф эпика; Task brief — бриф задачи; Vision — видение; Backlog — бэклог; Ready — готова к старту; In progress — в работе; BLOCKED — заблокирована; Review — ревью; Done — готово; Unmet dependency — невыполненная зависимость; Question — вопрос; Answer — ответ; Waiting for the owner — ждёт владельца; Conflict risk — риск конфликта; Parallel limit — лимит параллельной работы; Checkout — рабочая копия; Harness — клиент агента; Provider — провайдер; AgentRun — запуск; Review run — запуск ревью; Rework run — доработка; Unassigned — без задачи; Roles — роли (разработчик, ревьюер, архитектор, тестировщик, безопасность, DevOps, аналитик); CI state — состояние CI; Audit — аудит; Finding — находка; Migration plan — план перехода; Stranded document — бесхозный документ; Checkpoint — чекпойнт; Autopilot — автопилот; Autostart — автозапуск; Vault projection — проекция в Obsidian; Context pressure — заполненность контекста; Session artifact — файл сессии; Harness support level — уровень поддержки; Project registry — реестр проектов; Project Brain — знания проекта. The roadmap's statuses read не начат, спецификация, тикеты, в работе, готов; a Task's states read бэклог (`BACKLOG`), готова (`READY`), в работе (`ACTIVE`), заблокирована (`BLOCKED`), на ревью (`READY_FOR_REVIEW`), одобрена (`APPROVED`), готова к слиянию (`MERGE_READY`), слита (`MERGED`), готово (`DONE`), отменена (`CANCELLED`); CI reads проходит (`passing`), падает (`failing`), идёт (`running`), нет проверок (`none`); a finding reads в порядке (`ok`), пробел (`gap`), неизвестно (`unknown`). Git's words take their usual Russian, ветка and коммит; `worktree` stays.

1. Call the `binnacle` MCP server's `project_detect` tool. If this session has no `binnacle` MCP tools, run each Binnacle tool this skill calls as `binn call <tool> '<arguments as one JSON object>'` in the shell instead, with the same arguments, and read the JSON it prints: what the tool returns, or the same error with its code. If it fails, stop. Say what failed, worded from the error's code, message and `params`, and give the human the fix without running it yourself:
   - `daemon.unreachable`: `/binnacle:daemon start`, or `binn daemon start` at a terminal.
   - `project.not_registered`: `/binnacle:register`, or `binn project register` run in the main checkout.
   - If the shell cannot find `binn` (`command not found`, exit 127), `binn` is not on this harness's PATH (see the README's setup section).

   Binnacle is optional. Until it answers, the decisions still belong in the project's context file, ADRs, tickets, specs and roadmap: offer to draft, confirm and commit them as in steps 3 to 5, and skip step 6.
2. Call `checkpoint_prepare`, with no arguments. It records nothing. It returns the delta since the last checkpoint (the same fields as `daily_get`), `targets` and `attention`.
3. Draft the promotions. First read `knowledge.language` from `.binnacle/project.yaml`: `ru` is Russian, and `en`, any other value or none is English. Every draft is written in that repository language, whatever language this conversation is in, while the markers Binnacle parses stay English in every language: the roadmap's table header, its statuses, the Spec cell's `—`, `## Current focus` and `Next action:`, a ticket's header fields `Status:`, `Triage:`, `Blocked by:`, `Spec:` and `Roles:` with their values, the triage labels, and a spec's `## Risks`. Look at this session's conversation and at the delta, and find each durable decision that no canonical source holds yet. Leave out what is already written down, and anything that is not a decision. Classify each decision under one of the five `targets`, and write it into that target's path:
   - `vocabulary`: a domain term, which goes into the context file;
   - `trade_off`: a durable architectural trade-off, which gets a new ADR in the ADR directory;
   - `new_work`: a ticket in the tracker's issues directory, following the format of the tickets already there;
   - `product_rule`: a change to a spec in the specs directory;
   - `position`: the roadmap, meaning its status column and `## Current focus`.

   If a target's `path` is null, this project has no file for it. Show the decision anyway, and say that it cannot be written here.

   Also draft a fix for each attention item that the canonical sources can resolve and the derived part below does not, such as a `roadmap.status_mismatch` for an epic still `not started` with tickets.

   When `attention` holds `next_action.stale` or `next_action.missing`, draft the roadmap's `Next action:` paragraph as a `position` item: the paragraph that ends its current focus, starting with `Next action:` and ending with exactly one command in backticks, the one the human types for the next step, with the text you propose in full. Like every draft, it is written only once the human says yes (step 4).

   No ticket moves the current focus. The roadmap's derived part follows from the tickets alone, so it is written without a yes: an epic's status from `tickets` on, which is `done` exactly when every one of its tickets is `DONE` or `CANCELLED`, `in progress` while some are `DONE` and some open, and `tickets` while none is `DONE`, a `ready-for-human` ticket counting as any other; and the focus's *Done* line, the epics marked `done`. Read each epic's `progress` and the `roadmap.status_mismatch` items from `project_snapshot`, or the tickets' `Status:` lines when the daemon is down, and count nothing yourself. Only when that changes the roadmap, commit the roadmap alone, on the branch you are on, with a subject that says it is derived from the tickets, following the project's instruction files for the message and authorship; never push it. `not started` and `spec` stay a Product session's to write on the owner's yes, and so do the focus's other prose and the `Next action:`, in a commit of their own. A `position` draft that is only derived needs no yes: write and commit it now, calling `project_snapshot` once, with no arguments, for it, and show it in step 4 as written, with its commit.

   When the tickets' statuses have moved past the current focus's other prose, such as a ticket it says can start now `DONE`, draft its sentences on what is done and what can start as a `position` item, keeping the focus within the 2000 characters a fresh session reads of it. Like every draft but the derived part, it waits for the human's yes.
4. Show every draft, each with its kind, worded (a term, an ADR, a ticket, a spec change, the roadmap), its file and the exact text to add or change, and the branch the commit would land on, and the derived part as written, with its commit, or that nothing derived changed. Then stop and wait for the human. Nothing else is written until they confirm. They may edit, drop or add items. If they cancel, stop there and record nothing. If there is nothing to promote, say so and ask whether to record an empty checkpoint.
5. Write the confirmed items with your own file tools. Then commit only those files (`git add -- <paths>`), on the current branch. Follow `AGENTS.md` for commit messages and authorship. Do not push, merge or switch branches.
6. Call `checkpoint_record`, from this same checkout and after the commit, with `promoted` set to one `{ "type", "path" }` per committed item, the derived part's included. The path is relative to the project directory. Pass `[]` if nothing was promoted. It records this checkout's HEAD as the next checkpoint's baseline.
7. Report the recorded `head` and the promoted items. If `diagnostics` is not empty, word each one, a promoted file not committed (`checkpoint.uncommitted`) or a path that does not exist (`checkpoint.path_missing`), and do not call the checkpoint clean. Suggest committing or fixing the path and running `/binnacle:checkpoint` again. Do not do either without being asked.
