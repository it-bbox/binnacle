# Безопасность, приватность и устойчивость

_English version: [04-security-resilience.md](04-security-resilience.md). Этот файл — русский дубликат; обновляется вместе с `04-security-resilience.md`._

## Режим приватности по умолчанию

Предпочитайте telemetry, основанную на метаданных.

Хранить:

- идентификаторы run/task/project;
- временные метки;
- provider/model/profile;
- метрики токенов/cache;
- число/имена tool calls, где это настроено;
- переходы состояний.

Не требовать хранения:

- полных промптов;
- ответов модели;
- содержимого исходных файлов;
- секретов/аргументов инструментов.

Диагностика на уровне содержимого включается только явно.

## Секреты

- никаких API-ключей в `.binnacle/project.yaml`;
- используйте окружение/механизмы секретов ОС/конфиг upstream-клиента;
- никогда намеренно не экспортируйте секреты в Obsidian/Graphify;
- аудит должен находить очевидные риски закоммиченных секретов внешним/стандартным инструментом, если он будет добавлен позже, а не изобретать собственный сканер секретов.

## Учётные данные tracker

Запрашиваются с **областью только на чтение** — Binnacle никогда не пишет в tracker (`ADR-0013`), поэтому утёкший токен не может повредить репозиторий. Задаются в окружении демона как `BINNACLE_GITHUB_TOKEN` или `BINNACLE_GITLAB_TOKEN` либо в `~/.binnacle/credentials.json` с правами `0600`, по одному на хост, и никогда в `.binnacle/project.yaml` (`docs/operations/05-installation-checklist.ru.md`). Файл учётных данных, который могут читать другие, отвергается с `tracker.credentials_insecure`. Токен отправляется только на объявленный хост и никогда не появляется в ответе, диагностике, событии или строке лога. На GitHub это fine-grained токен с доступом на чтение к Issues, а также к Actions, Commit statuses и Pull requests для CI в snapshot (GitHub отдаёт check runs только GitHub Apps, поэтому Binnacle читает workflow runs и statuses коммита и никогда — его содержимое); на GitLab — токен с `read_api`. CI, прочитанный из Git remote, а не из tracker, идёт на хост, который называет remote и который не объявлял ни один манифест: на `github.com` или `gitlab.com` используется токен, хранимый для этого хоста, а на любом другом хосте — только запись файла учётных данных для него, никогда `BINNACLE_GITHUB_TOKEN` или `BINNACLE_GITLAB_TOKEN`, чтобы remote не мог вытянуть токен, предназначенный для другого хоста. Токены не импортируются из `gh` или `glab`: их токены обычно могут писать, и обещание выше перестало бы выполняться.

## Локальная сеть

HTTP-эндпоинты Daemon/Dashboard/MCP по умолчанию слушают только loopback, а loopback сам по себе не является границей аутентификации: любая вкладка браузера пользователя может достучаться до `127.0.0.1`. Поэтому каждый вызов API несёт токен из `~/.binnacle/`, а `Origin`/`Host` проверяются, чтобы отразить DNS rebinding. Учётных записей нет — пользователь один.

Без токена демон читает в одном эндпоинте, `GET /health`, который отвечает, слушает ли демон Binnacle и какой он версии, и больше ничего. Записи без токена он принимает в одном другом месте, `POST /v1/logs` OpenTelemetry (а также `/v1/metrics` и `/v1/traces`, на которые он отвечает, но не хранит), потому что экспортёр harness настраивается эндпоинтом и ничем больше: из события он сохраняет метаданные вызова и счётчики токенов и ни на какой вопрос не отвечает. Каждая операция — это `POST /ops/<operation>` и требует bearer-токен. `Host` должен быть ровно тем адресом, к которому привязан демон, — `127.0.0.1:<port>`, не `localhost:<port>` и не другим его именем; `Origin`, если он вообще отправлен, должен быть `http://` с тем же адресом. Обе проверки действуют и для `/health`, и для путей OpenTelemetry.

Любой удалённый/командный доступ — это post-MVP, и для него нужны отдельные аутентификация и модель угроз.

## Права на файлы

Всё, что Binnacle хранит о себе, лежит в домашнем каталоге Binnacle — по умолчанию `~/.binnacle`, переопределяется переменной окружения `BINNACLE_HOME`. Каталог создаётся с `0700`, а токен API, runtime-файл демона и лог демона — с `0600`.

`0600` и `0700` — понятия POSIX. **В Windows они не применяются.** Node передаёт режим, а файловая система его игнорирует. Там эти файлы защищены ACL профиля пользователя и ничем из того, что делает Binnacle, поэтому всё, что запущено под этой учётной записью Windows, может прочитать токен API. Это та же граница доверия, за которой уже лежат собственные файлы учётных данных harness, но это не защита, которую даёт Binnacle, — поэтому документ говорит об этом прямо, а не намекает на несуществующее принуждение.

## Восстановимость

SQLite — не единственный источник истины. Знание о проекте остаётся в Git/tracker/документах, а журнал telemetry/событий должен позволять осмысленное восстановление.

## Плавная деградация

Если отказывает любая опциональная возможность:

- Graphify недоступен → агенты используют Serena/исходники/документы;
- Obsidian недоступен → канонические документы не затронуты;
- Binnacle недоступен → обычный workflow агентов/Git продолжается;
- telemetry-адаптер недоступен → работа продолжается, метрики за этот интервал неполны и соответственно помечены.
