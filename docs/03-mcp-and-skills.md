# MCP and Skills Interface

## Goal

The developer should be able to work from Claude Code/Codex/etc. without repeatedly switching to a terminal or Dashboard.

MCP is the stable contract. Client-specific slash commands/skills are thin UX wrappers.

## Initial MCP surface

### Read-oriented

- `project.detect`
- `project.status`
- `project.snapshot` (the tool `project_snapshot`: the Product Snapshot, including each epic's `progress` in `roadmap.epics`, its Tasks `done` out of `all` of them, `CANCELLED` left out, `null` for an epic without a spec or when the Tasks cannot be read, and `roadmap.current`, the current epic: the epic furthest along, the first at the furthest status present in the order `in progress`, `tickets`, `spec`, `not started`, the roadmap's order deciding between equals, never a `done` one, `null` when every epic is done or there is none, which the Suggested step's rules and `task.list` read too; `next` — `action`, the roadmap's Next action, or `null` when the current focus does not end with one, and beside it `alternatives`, Binnacle's Suggested step (ADR-0032): a list of up to three, each with `kind` (`wait`, `parallel`, `resume`, `autopilot`, `byHand`, `owner`, `blocked`, `close`, `plan` or `finished`), `tasks`, the Task ids it names, `command` or `null`, an English `description` and provenance `calculated`, from the first of its eight rules that applies; a Task being worked on gives `wait`, then `parallel` when `tasks.parallel.free` is at least one and a Task is ready to start — and, when `tasks.parallel.impact` is available, only for a Task whose conflict risk with every Task in flight is `low`; without a graph the limit alone decides — and Tasks ready in the current epic give `autopilot` and `byHand`; `parallel` and `byHand` carry the ready Task's start command when exactly one is ready, and name several with none, so that no order is implied; a Task triaged `ready-for-human` is the owner's to do, so `parallel`, `autopilot` and `byHand` leave it out, and when every Task ready to start in the current epic is `ready-for-human`, one `owner` alternative names them with no command, while a Task with no triage counts as any other; an alternative whose command is the Next action's is left out; Binnacle's own commands — a Task's start command, `/binnacle:autopilot`, `/binnacle:product`, `/binnacle:roadmap` — are offered under any `workflow.provider`, and only Matt Pocock Skills' commands, a `plan` alternative's grilling, spec or tickets, are left out under any but `matt-pocock` (ADR-0042); a roadmap whose table lists no epic gives one `plan` alternative, `/binnacle:roadmap`; `alternatives` is empty when no rule applies, as without a roadmap, and `available: false` with the tracker's reason when the Tasks cannot be read — and `activity`, the runs running now and recently; `pendingDecisions`, *Waiting for the owner*, what only the owner can move, in three lists with the snapshot's limit and remainder: `questions`, every unanswered question of a Task neither `DONE` nor `CANCELLED`, each with its Task's `id`, `title` and `ticket`, its text as `question` and the `branch` it was read from, `null` for the checkout, read as `task.get` reads them, on GitHub or GitLab from the issues' comments, and not available, with the reason, when such a Task's comments cannot be read, `approvals`, the Tasks in `READY_FOR_REVIEW`, and `owner`, the Tasks triaged `ready-for-human` and ready to start, the whole section `available: false` with the tracker's reason when the Tasks cannot be read; `ci`, CI as the forge reports it, read at most once a minute, a failed read being read again on the next call, as a GitHub or GitLab tracker's Tasks are: `forge`, its `provider`, `host`, `repository` and `from`, `tracker` when the tracker is GitHub or GitLab with a repository, else `remote`, the first GitHub or GitLab Git remote, `origin` first, read with the token Binnacle holds for its host or anonymously, a remote's host other than `github.com` or `gitlab.com` with the credentials file's entry for it only, never the environment's token; `defaultBranch`, the forge's default branch with its latest `commit`, its `url`, `at`, the commit's time, and `state`; and `requests`, the open pull or merge requests with the snapshot's limit and remainder, each with its `number`, `title`, `branch`, `taskId`, the Task its branch maps to as usage maps a branch, or `null` when none does or when the Tasks cannot be read, which the snapshot's `tasks`, then `null`, tells apart, `draft`, `url` and `state`; every `state` is `{ value, provenance: 'provider_reported' }`, its value on GitHub from the commit's GitHub Actions workflow runs and combined status together, read with a fine-grained token's Actions, Commit statuses and Pull requests read access and no Contents access, so that the default branch's commit is the one its combined status names and its `at` is `null`, `failing` when any failed, was cancelled or timed out (any conclusion but success, skipped or neutral), `running` when any is queued or in progress, `passing` when all passed, `none` when it has neither, and on GitLab from a pipeline, the default branch's latest for its latest commit and a merge request's latest, whatever commit it ran on, `passing` on `success` or `skipped`, `running` while it is `created`, `waiting_for_resource`, `preparing`, `pending`, `running`, `scheduled` or `manual`, `failing` on `failed`, `canceled` or any other status, `none` when there is no such pipeline; a failing default branch is the attention item `ci.failing`; the section is `available: false` with the reason when there is no forge, or when anything of it cannot be read, the forge's 401, 403 or 429 among them, never part of it; every Task item of the snapshot carries `questions`, `asked` and `unanswered`, or `null` where its questions cannot be read, an issue whose comments failed or a closed GitLab issue, whose notes are not read; each Task in flight and ready to start carries `start`, the command that starts it, `/binnacle:task run <ticket>` with its ticket path or URL under any `workflow.provider`, and `roles`: `required`, the roles its ticket's `Roles:` line names in the baseline's form, matched case-insensitively, with `source` `ticket`, or Developer and Reviewer with `source` `default` when it names none, any other word being the attention item `task.unknown_role`, and `suggested`, Binnacle's suggestions, each with its `reason` and labelled `calculated`: an Architect when the Task touches 8 or more modules of the graph in `impact`'s reading, and Security when a touched module's path or the ticket's title and body hold `auth`, `token`, `secret`, `credential`, `password`, `permission` or `oauth`, or its plural, or `.env`, as a word or path segment, `.env.local` included, without a graph from the text alone, a role the line names never suggested; a `READY` Task with an attributed run is in flight, not ready to start, as the board reads it, and the daily's `readyToStart` leaves it out the same way; `tasks.parallel`, labelled `calculated`, gives how many Tasks may be worked on at once: `limit`, the Parallel limit, as autopilot reads it, with its `mode`, `number`, or `auto`, whose `limit` is its ceiling, 4, and its `source`, `manifest` for the manifest's `automation.max_parallel_development_tasks`, which wins for its project, `machine` for `parallelLimit` in the Binnacle home's `settings.json`, read on every call, or `default`, 2, where neither sets it (ADR-0041), `inProgress`, every Task in flight, and `free`, `limit` less `inProgress` and never below zero, one less `inProgress` under `auto` while `impact` is not available, since *auto* then runs one Task at a time, and `impact`, the conflict risk between every Task in flight and ready to start, read against the graph: `available: false` with the `graph` section's reason when there is no graph, or with `graphify-out/graph.json cannot be read as a graph`, and otherwise `tasks`, each Task's `id`, its `modules` (files of the graph) and `from`, `branch` when its branch (the one `task.get` names) has changed files since it left the default branch, read from that diff, or `ticket`, the modules its title and body name by path or by file name, and `pairs`, each pair's `tasks`, `risk` — `high` when they share a module, which `modules` names, `medium` when a module of one is a neighbour of a module of the other in the graph (one edge apart), which `modules` names, `low` otherwise, and `unknown` when either touches no module of the graph, never `low` — and `reason`; `impact`, each Task and each pair are labelled `calculated`; and `graph`, how fresh the Graphify graph the daemon keeps is (ADR-0036): `available`, whether there is a graph to use, with `reason` when not — `capabilities.graphify` declared `false`, `graphify` not on the daemon's PATH, or no `graphify-out/graph.json` built yet — `builtFrom`, the commit and time of the last successful run or `null`, `behind`, whether the default branch has moved past `builtFrom` (`null` when its commit cannot be read), and `lastRun`, the last run's `commit`, `at`, `outcome` (`built` or `failed`) and Graphify's `reason` when it failed, or `null` when none ran; and `autostart`, the daemon's own home's autostart (ADR-0043), read from the service's definition alone, never from the service manager: `state`, `on`, `off`, which a service installed for another home is too, or `broken`, installed but pointing at a Node or a daemon entry that no longer exists, with its `platform`, `home` and `command`, the one that changes it, `binn daemon autostart off` when it is on and `binn daemon autostart on` otherwise, which repairs a broken one; `available: false` with the reason when the definition cannot be read)
- `task.get` (the tool `task_get`: the Task brief, with the command that starts it, the Task's roles as the snapshot gives them, and the Task's Review — on the local tracker the text under `### Review` inside the ticket's `## Comments`, cut at the body limit, or `null` when the ticket records none; not available on GitHub or GitLab, whose comments Binnacle reads for questions only; and its questions, each `### Question` inside `## Comments` with the first `### Answer` after it and before the next Question, or `null` while unanswered, read from the ticket at the tip of the Task's branch while that branch is not merged into the default branch, `origin/HEAD`'s or else `main`, and from the caller's checkout otherwise, the branch they were read from named (ADR-0040); on GitHub or GitLab, each issue comment that starts with `### Question` or `### Answer`, its text the rest of the comment, in the order the comments were made, paired the same way — GitHub's issue comments of the repository through every page, matched to issues by number, and GitLab's notes of each open issue, system notes left out, a closed issue's not read — read with the tracker's read-only token on the declared host only, and not available, with the reason, when they cannot be read, the Tasks still read; and its `request`, the open pull or merge request whose branch maps to the Task as the snapshot's `ci` maps one, the first the forge lists when several do and wherever it falls in the list, with its `number`, `title`, `branch`, `draft`, `url`, `forge` and `state`, as the snapshot's `ci` gives them, only its own state read; `null` when none is open, and `available: false` with the reason whenever the snapshot's `ci` would be)
- `task.list` (the daemon's only, for the dashboard's board: an epic's Tasks, the current epic's (`roadmap.current`) unless a spec slug is given, each with its column, In progress read from runs where the ticket still says `READY`, its Unmet dependencies, whether its ticket records a Review (`null` on GitHub or GitLab), its `questions` counted as the snapshot counts them, its start command and its latest run, with its start and latest activity; `spec: null` gives a remote tracker's Tasks that carry no spec)
- `task.plan`
- `run.current`
- `run.list`
- `question.list`
- `review.status`
- `usage.get` (the tool `usage_get`: the project's token usage by Task and by role, each harness's support level, and derived metrics labelled as Binnacle's calculations; or one epic's, by its number on the roadmap (`epic`), over the Tasks of the spec the roadmap names for it, every Task listed with no remainder and the epic's averages, an epic the roadmap does not list or gives no spec refused with the reason; or one Task's, with its runs. The roles are `product`, `implementation`, `review`, `rework` and `unknown`, read from Git and the forge (`04-telemetry-dashboard.md`, *Run roles*). ### Controlled mutations

- `daily.get` (it records the baseline for the next daily; beside the delta it carries `pendingDecisions`, *Waiting for the owner*, as of now and as the snapshot gives it, over the Tasks at HEAD, and `ci`, as of now and as the snapshot gives it, its requests mapped to the Tasks at HEAD, with `ci.failing` among its attention items)
- `question.create`
- `question.answer`
- `checkpoint.prepare`
- `checkpoint.record` (ADR-0020: it records the checkpoint; the calling session writes the files)

With an Obsidian vault set on this machine, serving `project.snapshot` or `daily.get` also writes its note into the vault's Product folder, outside every repository (`operations/05-installation-checklist.md`, *The vault projection*).

The snapshot's attention includes `next_action.missing`, `next_action.stale`, which names a Next action whose command names a `DONE` or `CANCELLED` Task, or runs `/binnacle:autopilot` (or `binnacle-autopilot`) on an epic, by number or spec slug, that has tickets and none left for an agent, every one `DONE`, `CANCELLED` or `ready-for-human`, and `review.missing`, which names each `DONE` Task on the local tracker, not triaged `ready-for-human`, whose ticket records no Review, `graph.update_failed`, whose message names the failed commit and Graphify's reason while the last good graph is kept, and `graph.not_ignored`, when Git does not ignore `graphify-out/` and the daemon therefore runs nothing; a missing `graphify` is the `graph` section's reason, never an attention item. `ci.failing` names a default branch whose latest commit is failing on its forge, with the commit and its link; a failing pull or merge request is no attention item. `context.pressure` names an active Product session whose latest call read at least the manifest's threshold, or that compacted after the last recorded checkpoint, and suggests `/binnacle:checkpoint` (`04-telemetry-dashboard.md`, *Product session health*). `parallel_limit.invalid` names a `parallelLimit` in the Binnacle home's `settings.json`, or a file, that cannot be used, the limit then being 2. `vault.unwritable` names an Obsidian vault set in the Binnacle home's `settings.json` that does not exist or cannot be written; with no vault set there is none (`docs/operations/05-installation-checklist.md`, *The vault projection*). `daemon.autostart_broken` names a broken autostart for the daemon's home, what no longer exists, and the command that repairs it; autostart off is the user's choice and no attention item. The dashboard reads the same operations over the daemon's local API (ADR-0031), and adds no MCP tool.

Every attention item and diagnostic, `{ code, message }`, carries `params` too: the values its English `message` is written from — Task ids, tickets, paths, commits, numbers and names — as strings and numbers, with a `kind` naming which of its sentences a code with several takes, such as `tracker.unavailable`'s `token` or `repository`. An error envelope carries the same beside its `code` and `message`, and each of its `details` its own `code` and `params`, such as `expected.absolute_path` or `manifest.unknown_key`; `manifest.warning` carries its warning's code as `warning`. The field is additive: `code` and `message` are as they were, and the message stays English in MCP, `--json` and `binn call` (ADR-0045). A person's surface words the message in their language from its code and `params` with `@binnacle/core`'s `wordMessage`, one Russian sentence per code with `CONTEXT.md`'s Russian words, and shows the English message, marked as English, for a code it has no wording for or `params` it cannot use; in the chat, the model words it from its code, message and `params`. A test over the daemon's, core's and the adapters' sources fails when a code they emit has no wording.

The read-only audit is not an MCP tool: it is the CLI command `binn audit [path]` (`specs/audit-and-adopt/spec.md`), which needs no daemon, so an agent runs it as a command and reads `--json`: the findings of its areas, among them `docker`, `secrets` and `security`, each saying whether `binn init` closes it, and the migration plan built from them, `binn init` first, the secrets second, then one step per area (`operations/02-existing-project-adopt.md`, *Audit*). The skill `/audit` does exactly that and adds no tool and no daemon operation. It writes nothing; applying a recommendation is the human's, through `binn init`.

The machine's Parallel limit is read and set by the daemon's `parallel.get` and `parallel.set`, over its authenticated API, for the dashboard's Settings page alone: the set takes a whole number from 1 to 16 or `"auto"`, rewrites `parallelLimit` alone in the Binnacle home's `settings.json`, keeping every other key, and refuses anything else with `parallel_limit.invalid` and its reason, and a file it cannot read as a JSON object with `settings.unreadable`. `parallel.get` gives beside it the `informer`, each figure `calculated`: `mostActive`, the most runs active at once over every registered project's import window and when, `usageLimits`, each usage limit Claude Code recorded with the runs active then, and `notReporting`, the harnesses among those runs that record no usage limit. No tool reads or writes it (ADR-0041).

No tool writes to the tracker (ADR-0013). Closing an issue is done by the agent with its own tooling, or by the human in the tracker's own interface.

Do **not** expose autonomous `spawn_agents`, `merge_to_main`, `deploy_prod` in v1. `/autopilot` (ADR-0022) does not change this: it runs in the human's harness and uses the harness's own agents and Git, not Binnacle tools.

## Logical workflows / skills

Initial user-facing actions:

- `/product` — load Product role + compact current Product Snapshot;
- `/daily` — show delta since previous daily/checkpoint and attention items;
- `/task <id>` — load a compact task brief, ending with the command that starts the Task, `/binnacle:task run <ticket>`, Binnacle's own whatever the project's workflow, and none for a Task `DONE` or `CANCELLED` (ADR-0042); `/task run <ticket>`, with a ticket path, URL or Task id, works that ticket through the whole per-ticket process instead, which lives in that skill alone; the skill is model-invocable, so that autopilot's agents can run it, and `run` starts only when a human or an autopilot brief asks for it;
- `/status` — concise project and session status from `project_status` alone: the project, the manifest's tracker, this session's checkout (the registered one, or a linked worktree, said plainly) with its branch, commit and dirty state, and the diagnostics; the roadmap, Tasks and usage stay with `/product`;
- `/checkpoint` — extract durable delta and propose persistence; a stale or missing Next action paragraph is one of its candidates, with the text it proposes, written only on the human's yes;
- `/audit [path]` — run `binn audit --json` on the current repository or a path and show in the chat its migration plan first, then its gaps and unknowns by area, then the number of `ok`;
- `/init [path]` — run `binn init --plan --json` on the current repository or a path, show the whole plan in the chat and ask once, first asking whether the daemon starts at login when the plan's `autostart.ask` says it could be asked and passing that answer as `--autostart <yes|no>` to both calls; only the human's yes runs `binn init --apply <id>`, a changed plan is shown and asked again, and it never commits (ADR-0037);
- `/daemon [start|stop|status]` — run `binn daemon <action>`, `status` by default, and show what it printed, with the log tail of a failed start;
- `/register [path]` — run `binn project register` on a path, or else on the main checkout (the first path `git worktree list` prints), saying when that is not the session's checkout;
- `/dashboard` — run `binn dashboard`, which opens the dashboard in the browser, already authorised, and prints its address, which carries no token; answer that the dashboard opened at that address, and that if no browser appeared, `binn dashboard --print` at a terminal gives what to open there, never pasted into the chat; it never runs `binn dashboard --print`, because a skill's shell output reaches the model's provider and the token authorises the daemon's local API (ADR-0031);
- `/autopilot` — finish one planned epic with an agent per ticket; started only by a human (ADR-0022). Before its loop it drafts the plan's three questions from the spec and the tickets — what the epic can break, which step is the riskiest, and what was dropped and why — and, only on the owner's yes, writes them under the spec's `## Risks` and commits the spec alone to `main`; without a yes it starts nothing, and a spec that has them already is shown, with the question whether to go on, and not written again. Each agent runs `/binnacle:task run <ticket>`, which holds the per-ticket process, with a brief that adds only what being unattended asks (ADR-0042). A ticket triaged `ready-for-human` is the owner's: autopilot starts no agent for it and lists it under *Waiting for the owner*. Only tickets at low conflict risk run side by side: before starting a ticket beside one in flight, it reads `tasks.parallel.impact` from the snapshot and starts it only when the pair is `low`; a `medium`, `high` or `unknown` pair runs one after the other, and it says which pair and why; it reads the Parallel limit from the snapshot's `tasks.parallel`, and without Binnacle the manifest's value, or two; with `impact` not available, a number alone decides, *auto* runs one ticket at a time, and it says the risk was not assessed. Its agent records a question only the owner can answer as `### Question` in the ticket on its branch, in a commit of the ticket alone, and stops; started again on the epic, autopilot resumes a ticket whose branch exists unmerged and whose `questions`, at least one asked, are all answered, on that branch, removing the earlier worktree when it is clean and no daemon runs from it, and lists one with an unanswered question, or with a branch and no question, under *Waiting for the owner*, never starting either afresh (ADR-0040). Its review covers each role of the ticket's `Roles:` line beyond the Developer and the Reviewer under a `####` heading of its own, which it verifies. Its report gives `main`'s CI after the last push from the snapshot's `ci`, a failing or running one under *Waiting for the owner*, and ends with a proposed Next action paragraph, written and committed only on the owner's yes once the run has ended.
- `/answer [task]` — answer a question an agent recorded in a ticket; started only by a human, and an agent never answers a question, its own or another's (ADR-0040). It lists the snapshot's unanswered questions, or goes to the named Task's through `task_get`, takes the owner's answer from the chat as given, and writes it: on the local tracker into the ticket, as `### Answer` with the date right after the question's text, committed with nothing but the ticket on the Task's branch while it is unmerged, in the worktree that has the branch checked out or a temporary one it removes, and otherwise in the caller's checkout; on GitHub or GitLab as an issue comment starting with `### Answer`, through `gh` or `glab`, its body from a file rather than the command line; such a comment answers only the issue's latest question while it is unanswered, which the skill says before posting. It never pushes, checks with `task_get` that the answer is read, and ends with `/autopilot <epic>` for a Task of an epic at `tickets` or `in progress`, which resumes the ticket on its branch, or with the Task's start command otherwise.
- `/roadmap [new | existing]` — turn a vision or a half-built project into a roadmap of epics, started only by a human, with no daemon: it reads files, Git and `binn audit --json`, picks its entry from the history and the source files, and says which. A new project's vision is read from `<knowledge.docs>/vision.md`, or asked for one question at a time and written in the owner's words; an existing project's epics are proposed `done`, `in progress` or `not started` with their specs linked, with a destination for each stranded document and a roadmap not in the format rewritten into it, keeping its content. It writes the rows, a `## Epics` section and a Next action that grills the first epic not done, and commits only what it wrote, all on the owner's yes, never pushing. Run again, it proposes additions and reorders among the epics not started, never touching a `done` epic or a row that links a spec.
- `/help` — a plain guide to working with Binnacle, in the language the user writes in: what Binnacle is, each skill of the plugin with when to use it, grouped as setting up, a day's work and planning, and the usual order of a day (`/product`, the work, `/checkpoint`); it calls no tool, runs no command and needs no daemon.

Every skill gives each command it offers the human alone in a fenced block, which copies in one click: a skill such as `/binnacle:daemon start` in a plain fence, a shell command such as `binn daemon start` in a `bash` fence. The roadmap's `Next action:` paragraph keeps its one command in backticks, the snapshot's contract; a skill fences it when it shows it.

The skills reach a harness through one of two channels, from one text per skill (ADR-0039). The text names no harness's mechanism: it says to ask the human, to start a background agent in a worktree of its own, or to open a new session, and takes what depends on the harness from `binn`'s output.

- **Claude Code** serves them as a plugin named `binnacle` (ADR-0023), so each is namespaced: `/binnacle:product`, `/binnacle:daily`, `/binnacle:task`, `/binnacle:status`, `/binnacle:checkpoint`, `/binnacle:audit`, `/binnacle:init`, `/binnacle:daemon`, `/binnacle:register`, `/binnacle:dashboard`, `/binnacle:autopilot`, `/binnacle:answer`, `/binnacle:roadmap` and `/binnacle:help`. Other projects get the plugin from the installed npm package (ADR-0027).
- **Every other harness** the `skills` CLI (skills.sh) detects, such as Codex, Antigravity, ZCode or Pi, gets the package's copy of the same skills, named `binnacle-<action>`: `binnacle-product`, `binnacle-daily`, `binnacle-task`, `binnacle-status`, `binnacle-checkpoint`, `binnacle-audit`, `binnacle-init`, `binnacle-daemon`, `binnacle-register`, `binnacle-dashboard`, `binnacle-autopilot`, `binnacle-answer`, `binnacle-roadmap` and `binnacle-help`. The package's build writes the copy from the plugin, renaming each skill and rewriting every `/binnacle:<action>` in the text, so a skill names the others the way the harness reading it does, and gives each the plugin's version under `metadata`. `binn init` installs it at user scope with `npx skills add <the copy> -g -y --json`, then takes it back out of Claude Code, which has the plugin, with `npx skills remove -g -a claude-code`, and out of each harness named with `--skip-harness`; after installing another harness, running `binn init` again installs them into it, stale or current, and says which they were. `binn audit` reports a copy in `~/.agents/skills` at another version than the package's as `capabilities.binnacle_skills`, and `binn init`'s plan reinstalls it.

Where a harness cannot start a background agent in a worktree of its own, `binnacle-autopilot` refuses at its first step and changes nothing, and the epic's tickets are run by hand; it sends a push notification only where the harness can.

`/audit`, `/init`, `/daemon`, `/register`, `/dashboard` and `/roadmap` need no daemon: they run `binn` or read files in the harness's shell, not an MCP tool, so they can be started while the daemon is stopped. `/register` and `/dashboard` then fail with `binn`'s message and name `/daemon start`. `/init` then leaves registration out of its plan, and says that `/daemon start` then `/register` adds it, as `/daemon start` names `/register` for a project not registered yet. When `/init` created `.mcp.json`, it ends by saying to open a new session in the repository and approve the project's `binnacle` server, since Claude Code reads `.mcp.json` only when a session starts. Where `/product`, `/daily`, `/task`, `/status`, `/checkpoint`, `/autopilot` and `/answer` meet `daemon.unreachable` or `project.not_registered`, they name `/binnacle:daemon start` or `/binnacle:register` beside the `binn` command.

## How the interface reaches a harness

MCP is the universal path, and registering it is a config edit in a location each harness already defines — `~/.claude.json` or a project's `.mcp.json` for Claude Code, `[mcp_servers.*]` in `~/.codex/config.toml` or a trusted project's `.codex/config.toml` for Codex. `binn init` performs that registration as part of one plan of every write, shown whole and confirmed once (ADR-0034; Enter accepts it at a terminal, and without a terminal nothing is written; from a chat, `binn init --plan --json` prints the plan with its id, and after the human's yes in the chat `binn init --apply <id>` writes that plan and no other, exiting 3 with `init.plan_changed` when the plan is no longer the one shown, ADR-0037), from one config template per known harness — Claude Code, Codex, opencode and VS Code to start with — and prints a generic stdio snippet for any other. Its Summary then suggests `binn audit`, names the harnesses the `skills` CLI installed Binnacle's skills into, and, for each detected harness other than Claude Code, says to run `binnacle-product` there. Supporting another harness's MCP registration is adding a template; a harness without one reaches the tools through `binn call`, below. This is support level 1 from ADR-0014, and it requires no adapter code.

Command wrappers are generated from a single procedure description per action, so supporting a new harness means adding an output template, not new logic. A harness with no wrapper mechanism still works: the human asks for the tool by name.

Both MCP transports are served — stdio for harnesses that spawn processes, Streamable HTTP from the daemon for those that prefer an endpoint. The tool implementations behind them are the same.

A harness with a shell and no Binnacle MCP server — one without MCP, or one whose `binnacle` server is not registered yet — reaches the same tools through `binn call <tool> [json]` (ADR-0039). It reads the same tool table and makes the same daemon call as `binn mcp`, so a tool exists in both or in neither, and it answers for the project containing the working directory. The arguments, if the tool takes any, are one JSON object, such as `binn call task_get '{"id":"<task id>"}'`, checked against the tool's schema as the MCP server checks them, and a tool that takes none is called with none. It prints what the tool returns as JSON on stdout and exits 0; the daemon's error envelope, the same the tool returns, on stdout with exit 3, or with exit 4 when it is `daemon.unreachable`; and an unknown tool, or arguments that are not JSON or that the tool does not take, as a message on stderr with exit 2. `binn call --help` lists the tools and their arguments. Each skill that calls a tool — `/product`, `/daily`, `/task`, `/status`, `/checkpoint`, `/autopilot` and `/answer` — says once to call the `binnacle` MCP tool and, where the session has none, to run `binn call` with the same arguments in the shell and read its JSON.

## Harnesses and their levels

Every harness with MCP or a shell is at level 1, Context. Above it, Binnacle reads what each harness leaves on this machine, and receives the OpenTelemetry of those that export it, which `binn init` configures (ADR-0014, ADR-0038). Each level is the highest one a harness can reach: a project's actual level, and the reason a harness stays below the next one, are in `usage.get` and on the dashboard's usage page.

| Harness | Level | How Binnacle reaches it |
| --- | --- | --- |
| Claude Code (CLI and desktop) | 4 — Live | its session files under `~/.claude/projects` (`$CLAUDE_CONFIG_DIR/projects`); its OpenTelemetry, `claude_code.api_request` events, which `binn init` enables in its settings' `env` |
| Codex (CLI and desktop) | 4 — Live | its rollouts under `~/.codex/sessions` (`$CODEX_HOME/sessions`); its OpenTelemetry, `codex.sse_event` events, which `binn init` enables in the `[otel]` table of `~/.codex/config.toml` |
| Gemini CLI | 4 — Live, not verified | its session files under `~/.gemini/tmp/<project>/chats` (`$GEMINI_CLI_HOME/.gemini/tmp`); its OpenTelemetry, `gemini_cli.api_response` events, which `binn init` enables in the `telemetry` block of `~/.gemini/settings.json`. Its events name no directory, so they wait in no project until a session file names one, though while they arrive they make Gemini CLI live in every project's level |
| opencode | 3 — Usage | its SQLite database, `opencode.db` in `~/.local/share/opencode` (`$XDG_DATA_HOME/opencode`), one record per finished call; it documents no OpenTelemetry export |
| ZCode | 3 — Usage | its SQLite database, `~/.zcode/cli/db/db.sqlite`, one record per row of `model_usage`, with its provider and model, such as GLM, apart; it documents no OpenTelemetry export |
| pi | 3 — Usage | its session files under `~/.pi/agent/sessions` (`$PI_CODING_AGENT_DIR/sessions`), one record per entry pi totals; it has no built-in OpenTelemetry export, and `binn init` installs none |
| Antigravity | 2 — Attribution, not verified | its window state, `Antigravity/User/globalStorage/state.vscdb` in VS Code's user data directory, which names each conversation's workspace, and its conversations under `~/.gemini/antigravity/conversations`. They are encrypted and it has no exporter, so a record is a conversation with no model and no tokens |
| any other | 1 — Context | MCP, or `binn call` in its shell |

Level 4 holds while a harness's events arrive: within the last ten minutes. Without the export, or before it was configured, Claude Code, Codex and Gemini CLI are read at level 3 from their files, and a call seen both ways is counted once. `binn init`'s Summary and `binn audit` name each detected harness that cannot export, with the same reason. Gemini CLI and Antigravity are built from their sources and descriptions, and marked not verified: on the owner's machine, Gemini CLI no longer signs in with a personal Google account and Antigravity's model answered only with quota errors (`specs/telemetry-for-any-harness/spec.md`, *Further Notes*). opencode's database is read as its source describes it, until the exit demonstration confirms it on a real install.

## Skill design rule

Skills contain procedure, not project state.

Example `/daily` skill:

1. Detect project through Binnacle MCP.
2. Request daily delta.
3. Present changes and attention items.
4. Do not mutate project state unless explicitly asked.

## Direct specialized MCPs stay direct

Do not make Binnacle a proxy for every MCP:

- Serena remains directly available to coding agents;
- Context7 remains directly available;
- Graphify can be direct or adapter-backed depending on client/workflow.

Binnacle owns project/task/run state, not all tool calls.
