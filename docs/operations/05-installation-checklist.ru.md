# Чек-лист установки

_English version: [05-installation-checklist.md](05-installation-checklist.md). Этот файл — русский дубликат; обновляется вместе с `05-installation-checklist.md`._

Этот чек-лист отделяет требования Binnacle от рекомендуемых внешних возможностей. Точные upstream-команды стоит перепроверять при реализации, потому что сторонние установщики меняются.

`binn init` устанавливает Serena, Graphify и ast-grep, когда их нет, после одного «да» на план, командами ниже; для первых двух ему нужен `uv`, для ast-grep — `npm`, и если их нет, он их называет, а не устанавливает. Таблица, по которой он устанавливает, — в `docs/operations/03-external-tools.ru.md`, *Что устанавливает `binn init`*.

В том же плане, после установок, `binn init` регистрирует MCP-серверы Serena, Context7 и Graphify в каждом найденном harness, через собственный CLI harness и никогда в репозитории: на уровне пользователя через `claude mcp add --scope user`, `codex mcp add` (`~/.codex/config.toml`) и `code --add-mcp` (профиль пользователя VS Code). Сервер Graphify обслуживает граф одного проекта, поэтому он регистрируется на локальном уровне Claude Code (`~/.claude.json`, только для этого проекта) и печатается для остальных. opencode, у которого нет неинтерактивной команды для этого, получает каждую запись напечатанной. Уже зарегистрированный сервер не трогается, кроме Serena в пользовательском файле Codex с контекстом Claude Code, которую план регистрирует заново с контекстом Codex. Команды — в `03-external-tools.ru.md`, *MCP-серверы, которые он регистрирует*.

## Установка Binnacle

Binnacle поставляется через npm и требует Node 24 на машине пользователя (`ADR-0016`):

```bash
npm i -g @it-bbox/binnacle
```

Он работает нативно на Linux, macOS и Windows. Демон запускается командой `binn daemon start`. `binn init` спрашивает, запускать ли его при входе в систему, по умолчанию да, и настраивает это через собственный менеджер служб пользователя: пользовательский unit systemd в Linux, LaunchAgent в macOS, задачу Планировщика заданий при входе в Windows. Без терминала он ничего не устанавливает и вместо этого называет команду. `binn daemon autostart on|off` меняет это позже, а `binn daemon autostart` без аргумента говорит, включён ли автозапуск, выключен или сломан, и для какого домашнего каталога Binnacle (ADR-0043).

Его настраивают пять переменных окружения, все их демон читает из своего окружения:

| Переменная | По умолчанию | Значение |
| --- | --- | --- |
| `BINNACLE_HOME` | `~/.binnacle` | Где Binnacle хранит runtime-файл демона, токен API, хранилище, файл учётных данных tracker и файл настроек этой машины. Укажите другой каталог, чтобы запустить одноразовый экземпляр рядом с настоящим. |
| `BINNACLE_PORT` | `7717` | Loopback-порт, к которому привязывается демон. `0` берёт эфемерный порт. |
| `BINNACLE_GIT_TIMEOUT_MS` | `5000` | Сколько может длиться один вызов `git` только на чтение, прежде чем `project.status` сообщит, что факты Git недоступны. Увеличьте для репозитория на медленной файловой системе. |
| `BINNACLE_GITHUB_TOKEN` | нет | Токен только на чтение для каждого проекта, чей `tracker.provider` — `github`, и для CI каждого проекта, чей Git remote на `github.com`. |
| `BINNACLE_GITLAB_TOKEN` | нет | Токен только на чтение для каждого проекта, чей `tracker.provider` — `gitlab`. |

### Учётные данные tracker

Проект на GitHub или GitLab issues читается токеном только на чтение: на GitHub это fine-grained токен с доступом на чтение к Issues, на GitLab — токен с `read_api` (`docs/operations/04-security-resilience.ru.md`). Публичному репозиторию токен не нужен.

CI в snapshot читается тем же токеном: из tracker, когда это GitHub или GitLab, а иначе — из первого Git remote проекта на GitHub или GitLab, с токеном, хранимым для хоста этого remote: на `github.com` — `BINNACLE_GITHUB_TOKEN` или запись `github.com` в файле учётных данных; на любом другом хосте — только запись файла учётных данных для него, так как токен окружения предназначен для объявленного хоста. На GitHub fine-grained токену тогда нужен ещё и доступ на чтение к Actions, Commit statuses и Pull requests: Binnacle читает workflow runs GitHub Actions и statuses коммита, так как GitHub отдаёт check runs только GitHub Apps, и fine-grained токену их не выдать; `read_api` на GitLab покрывает его pipelines и merge requests.

Для одного хоста или нескольких храните токены в `credentials.json` в домашнем каталоге Binnacle (`~/.binnacle/credentials.json`): JSON-объект с ключами — `tracker.host` проекта ровно так, как его пишет манифест, или `github.com` либо `gitlab.com`, если манифест его не пишет.

```json
{
  "github.com": "github_pat_…",
  "gitlab.example.com": "glpat-…"
}
```

Сделайте его доступным только владельцу (`chmod 600 ~/.binnacle/credentials.json`). Файл, который может читать или писать кто-то ещё, не читается вовсе, и snapshot сообщает `tracker.credentials_insecure`. Binnacle читает этот файл и никогда его не пишет.

При каждом вызове демон сначала берёт переменную провайдера, затем запись хоста в файле, а иначе читает анонимно. `GITHUB_TOKEN` и другие общие имена не читаются, и ничего не берётся из `gh` или `glab`: их токены обычно могут писать. Переменная читается из окружения, с которым запустился демон, поэтому после её изменения перезапустите его; файл читается при каждом вызове.

На один домашний каталог Binnacle работает один демон. `binn daemon status` сообщает, запущен ли он и где; `binn daemon stop` его останавливает. Коды выхода: `0` успех, `2` ошибка использования, `3` операция не удалась, `4` демон недоступен.

### Dashboard

Демон также раздаёт dashboard только для чтения по своему адресу, по умолчанию `http://127.0.0.1:7717/`. `binn dashboard` открывает dashboard в браузере по умолчанию, уже авторизованным, а `binn dashboard --print` печатает его адрес, ничего не открывая. После первого раза обычный адрес работает в этом браузере как закладка.

### Когда harness не находит binn

Harness, который отвечает `command not found` на `binn`, не видит в своём PATH глобальный каталог исполняемых файлов npm. `npm prefix -g` печатает глобальный префикс npm; `binn` — это `<prefix>/bin/binn` в Linux и macOS и `<prefix>\binn.cmd` в Windows. Desktop-приложение Claude Code не читает файл запуска shell, например `~/.bashrc`, поэтому заданный там PATH до него не доходит: положите скрипт-обёртку с именем `binn`, исполняемым, в каталог, который уже есть в PATH приложения, — в Linux это `~/.local/bin`, — с префиксом, записанным явно:

```sh
#!/bin/sh
exec "<prefix>/bin/binn" "$@"
```

При разработке Binnacle из checkout `binn` запускается через pnpm: см. [CONTRIBUTING.ru.md](../../CONTRIBUTING.ru.md#binn-в-desktop-приложении-claude-code), *binn в desktop-приложении Claude Code*.

### Claude Code

Текущий upstream даёт путь установки как plugin Claude:

```text
/plugin install mattpocock-skills
```

### Codex и другие совместимые агенты

Текущий upstream документирует:

```bash
npx skills@latest add mattpocock/skills
```

`binn init` выполняет ту же установку за вас, на уровне пользователя, в каждый harness, который находит CLI `skills`, затем удаляет установленные навыки из Claude Code, у которого есть plugin (`03-external-tools.ru.md`, *Плагины навыков, которые он устанавливает*). Он пропускает её, если манифест объявляет Matt Pocock Skills `false` или он не находит ни одного harness. Команда выше — путь без `binn init`.

`binn init` пишет в каждом репозитории соглашения, которые читают эти навыки, поэтому никакой навык настройки не запускается первым. Используйте согласованную цепочку проектирования, когда это уместно:

```text
/grill-with-docs
/to-spec
/to-tickets
```

`binn init` обнаруживает существующую установку и никогда не переустанавливает вслепую: он ставит plugin Matt Pocock Skills для Claude Code в своём плане, когда Claude Code найден и его не показывает, и не трогает уже показанный; вместо `/setup-matt-pocock-skills` он пишет файлы соглашений и блок *Agent skills* там, где их нет (`03-external-tools.ru.md`, *Плагины навыков, которые он устанавливает*).

## Рекомендуется: Serena

Serena — специализированный MCP для семантической навигации и редактирования кода на уровне символов.

Текущий upstream quick start использует `uv`; `binn init` выполняет установку, когда `serena` нет в `PATH`:

```bash
uv tool install -p 3.13 serena-agent
serena init
```

Для CLI-агентов Serena поддерживает автоопределение проекта по текущему рабочему каталогу через `--project-from-cwd` при настройке своего MCP-сервера.

Binnacle должен проверять здоровье/доступность Serena и активацию проекта, но не должен проксировать полный API Serena.

## Рекомендуется: Graphify

Graphify — поставщик графа архитектуры/зависимостей в профиле Standard.

Установите базовый CLI; `binn init` выполняет это, когда `graphify` нет в `PATH`:

```bash
uv tool install graphifyy
```

Его MCP-серверу нужен extra `mcp`. `binn init` регистрирует его для этого проекта на локальном уровне Claude Code, запуская в собственном окружении:

```bash
claude mcp add --scope local graphify -- uv run --no-project --with 'graphifyy[mcp]' python -m graphify.serve <project>/graphify-out/graph.json
```

Регистрируйте интеграции с ассистентами по текущим upstream-инструментам, например установкой на уровне проекта, где это уместно:

```bash
graphify install --project
```

`binn init` строит первый граф последним в своём плане, с `graphify-out/`, добавленным в `.gitignore`, если Git его ещё не игнорирует, запуская извлечение Graphify только по коду из корня проекта, а затем его отчёт; ни тому, ни другому не нужен API-ключ, и ни то, ни другое не вызывает модель; после этого демон держит граф актуальным (`03-external-tools.ru.md`, *Первый граф, который он строит*):

```bash
graphify extract . --code-only --allow-dedup-shrink
graphify cluster-only . --no-label
```

Сгенерированный результат включает машиночитаемый граф и отчёт об архитектуре.

Для проекции в Obsidian Graphify поддерживает явный экспорт в существующее хранилище. Не делайте этот экспорт каноническим хранилищем.

Политика игнорирования проекта по умолчанию обычно должна исключать:

```text
.scratch/**
node_modules/**
.nuxt/**
.output/**
dist/**
coverage/**
```

Настройте сгенерированные/vendor-каталоги под каждый проект.

## Опционально: Obsidian

Установите desktop-приложение Obsidian вручную — для представления знаний человеку.

Конфигурация зависит от машины/пользователя. **Никогда не коммитьте абсолютный путь к личному хранилищу** в общую конфигурацию проекта.

### Файл настроек

Хранилище задаётся в `settings.json` в домашнем каталоге Binnacle (`~/.binnacle/settings.json`), собственных настройках этой машины, вне любого репозитория. Сделайте его доступным только владельцу, как файл учётных данных (`chmod 600`):

```json
{
  "obsidian": { "vaultPath": "/home/me/Notes" }
}
```

`binn init` предлагает путь в своём плане, после дописывания в `.gitignore` и перед первым графом, когда файл не называет хранилища: он читает собственный список хранилищ Obsidian на этой машине (`obsidian.json` в каталоге конфигурации Obsidian: `~/.config/obsidian` в Linux или его Flatpak или Snap; `~/Library/Application Support/obsidian` в macOS; `%APPDATA%\obsidian` в Windows), и если там ровно одно хранилище, план записывает его в файл настроек, доступный только владельцу, сохраняя все остальные настройки файла. Если хранилищ нет или их несколько, он ничего не предлагает, называет найденные и говорит, как задать путь. Чтобы выбрать другое хранилище, чем предложенное, отклоните план и отредактируйте файл. Уже заданный путь отмечается и не трогается, и в репозитории этим шагом ничего не пишется.

Путь абсолютный и указывает на собственный каталог хранилища. Демон читает файл при каждом опросе и каждом snapshot, поэтому изменение действует без перезапуска. Нет файла или нет `obsidian.vaultPath` — нет проекции и нет пункта внимания.

В том же файле хранится Parallel limit (ADR-0041), `parallelLimit`: целое число от 1 до 16 или `"auto"`; 2, если не задан. Страница Settings в dashboard пишет его через демон, сохраняя все остальные ключи; `automation.max_parallel_development_tasks` в манифесте проекта побеждает для своего проекта.

### Проекция хранилища

Когда хранилище задано, демон ведёт одностороннюю проекцию каждого зарегистрированного проекта в `<Vault>/Projects/<Project>/`, где `<Project>` — `project.name` манифеста или его id (ADR-0036):

| Папка | Что в ней |
| --- | --- |
| `Product/` | `roadmap.md`, из `<knowledge.docs>/roadmap.md`; `snapshot.md` и `daily.md`, последние отданные snapshot и daily |
| `Specs/<slug>/` | `spec.md` и тикеты спеки, из `knowledge.specs` |
| `Decisions/` | ADR, из `knowledge.adr` |
| `Research/` | остальной Markdown из `knowledge.docs`, в той же раскладке, без roadmap |
| `90-Graphify/` | `GRAPH_REPORT.md`, отчёт Graphify о последнем успешном построении графа |

Раз в минуту он читает ветку по умолчанию каждого проекта, и когда ветка сдвинулась, настройка хранилища изменилась или граф был построен заново, он заново отрисовывает проект из этого коммита, читая через Git: незакоммиченное изменение в checkout никогда не попадает в хранилище. Относительные Markdown-ссылки между спроецированными файлами становятся ссылками Obsidian.

Заметки snapshot и daily пишутся каждый раз, когда отдаётся snapshot или daily, из того, что было отдано, без дополнительного обращения к tracker: их `source` — `project.snapshot` или `daily.get`, их `commit` — HEAD вызывающего, а строка `served:` даёт время. Обе содержат *Waiting for the owner*: неотвеченные вопросы, задачи, ждущие одобрения, и задачи `ready-for-human`, готовые к старту. Их тикеты и ADR ссылаются на спроецированные заметки. Если хранилище не задано, отдача ничего не пишет.

`90-Graphify/GRAPH_REPORT.md` — это `graphify-out/GRAPH_REPORT.md` в зарегистрированном checkout, с коммитом последнего успешного запуска. Он переписывается только после более нового успешного запуска, поэтому неудачный запуск оставляет его как есть, а хранилище, заданное после неудачного запуска, не получает отчёта до следующего успешного. Без записанного успешного запуска, без отчёта или с `capabilities.graphify: false` заметки нет, как нет и пункта внимания о ней.

Каждая заметка, которую он пишет, начинается с frontmatter, называющего её сгенерированной, с её источником и коммитом:

```yaml
---
generated-by: binnacle
source: docs/adr/ADR-0036-the-daemon-maintains-derived-graph-and-vault.md
commit: <hash>
---
```

Демон пишет, переписывает и удаляет только файлы с этой меткой, поэтому ваша заметка рядом с ними или ваш файл по пути сгенерированной заметки остаётся байт в байт. Сгенерированная заметка, чей источник исчез из ветки по умолчанию, удаляется. Каждая запись — целый файл, через временное имя и переименование. Правка сгенерированной заметки перезаписывается при следующем обновлении и никогда не синхронизируется обратно. Проекция производная: удаление папки проекта ничего не теряет, и она возвращается при следующем движении ветки или следующем старте демона.

Путь к хранилищу, который не существует, не является каталогом или недоступен для записи, а также файл настроек, который не читается, — это пункт внимания snapshot `vault.unwritable`.

## Проверка capability telemetry

`binn init` настраивает экспорт OpenTelemetry каждого найденного harness, у которого он есть, в его настройках на уровне пользователя, внутри своего одного плана и после его одного подтверждения (спека эпика 10, *`binn init`'s telemetry step*). Экспорт направляется на адрес демона — адрес запущенного демона, а иначе `http://127.0.0.1:` и `BINNACLE_PORT` или 7717 — как OTLP JSON поверх HTTP, с выключенным логированием промптов:

| Harness | Настройки | Что добавляет план |
| --- | --- | --- |
| Claude Code | `settings.json` в `CLAUDE_CONFIG_DIR` или `~/.claude`, слиянием, с сохранением остального | `env`: `CLAUDE_CODE_ENABLE_TELEMETRY=1`, `OTEL_LOGS_EXPORTER=otlp`, `OTEL_EXPORTER_OTLP_PROTOCOL=http/json`, `OTEL_EXPORTER_OTLP_ENDPOINT=<address>` |
| Codex | `config.toml` в `CODEX_HOME` или `~/.codex`, дописыванием | `[otel]` с `exporter = { otlp-http = { endpoint = "<address>/v1/logs", protocol = "json" } }` и `log_user_prompt = false` |
| Gemini CLI | `.gemini/settings.json` в `GEMINI_CLI_HOME` или `~`, слиянием, с сохранением остального | `telemetry`: `enabled: true`, `target: "local"`, `otlpEndpoint: "<address>"`, `otlpProtocol: "http"`, `logPrompts: false` |

Собственные настройки OpenTelemetry harness, экспортируют ли они куда-то ещё или никуда, не трогаются и называются в Summary: `env` Claude Code с любой переменной `OTEL_`, файл Codex с таблицей `[otel]`, файл Gemini CLI с блоком `telemetry` — если это ещё не экспорт выше. Файл настроек, который не является чистым JSON, например с комментариями, не переписывается: изменение печатается. Если демон не запущен и `BINNACLE_PORT` равен 0, адреса нет, и шаг пропускается. Найденный harness, который не умеет экспортировать, — opencode и VS Code, — называется в Summary с причиной. Проверка готовности telemetry в `binn audit` читает те же настройки и сообщает для каждого найденного harness, экспортирует ли он в Binnacle (`telemetry.export_<harness>`).

Не проваливайте инициализацию проекта из-за того, что у одного провайдера нет богатой telemetry.

## Ожидаемый Summary `binn init`

Пример целевого UX:

```text
Binnacle                       ✓
Git                               ✓
Node 24 LTS                       ✓
pnpm                              ✓
Matt Pocock Skills                ✓ configured / action required
Ponytail                          ✓ / optional action
Serena                            ✓
Graphify                          ✓ / install suggested
Context7                          ✓ already configured
ast-grep                          ✓
Obsidian                          optional / configured path missing
Telemetry: Claude Code            ✓
Telemetry: Codex                  ✓
Telemetry: Gemini                 not configured
Tracker                           GitHub Issues
Automation mode                   MANUAL
```

Команда настройки объясняет свои действия, показывая их одним планом — и записи внутри репозитория, и изменения вне его, — и просит одного подтверждения всего плана (ADR-0034): в терминале Enter принимает его, `n` отклоняет, а без терминала ничего не записывается. Вопросы, которые не касаются записи, например окно импорта истории, задаются до плана; так же и вопрос, запускать ли демон при входе в систему, чьё «да» становится последним пунктом плана, `binn daemon autostart on`, — он задаётся, только пока автозапуск для этого домашнего каталога выключен, и только в терминале.
