# Внешние инструменты и профиль установки

_English version: [03-external-tools.md](03-external-tools.md). Этот файл — русский дубликат; обновляется вместе с `03-external-tools.md`._

Этот документ описывает **рекомендуемые интеграции**, а не зависимости, которые надо встраивать в Binnacle.

## Что устанавливает `binn init`

`binn init` устанавливает инструменты профиля Standard, которые являются исполняемыми файлами (ADR-0035), в своём одном плане (ADR-0034), вне репозитория, только через менеджер пакетов:

| Инструмент | Как обнаруживается | Что нужно заранее | Команда установки |
| --- | --- | --- | --- |
| Serena | `serena` в `PATH` | `uv` | `uv tool install -p 3.13 serena-agent` |
| Graphify | `graphify` в `PATH` | `uv` | `uv tool install graphifyy` |
| ast-grep | `ast-grep` в `PATH` (никогда не `sg`) | `npm` | `npm i @ast-grep/cli -g` |

Инструмент, который уже есть в `PATH`, отмечается как найденный и не трогается. Инструмент, который манифест объявляет `false` в `capabilities`, не предлагается. Недостающая предпосылка называется вместе с командой, которая её ставит, а зависящие от неё инструменты не входят в план: init никогда не ставит `uv` и никогда не запускает скрипт-установщик. Каждая установка попадает в Summary, и неудачная не останавливает остальные. Манифест, который создаёт init, объявляет `true` в `capabilities` для каждого инструмента, который он установил или нашёл. Таблица — это `apps/cli/src/tools.ts`, её читает и `binn audit`.

### Плагины навыков, которые он устанавливает

Matt Pocock Skills и Ponytail поставляются как плагины Claude Code. Init устанавливает их через CLI плагинов Claude Code, на уровне пользователя, вне репозитория, так же как плагин `binnacle`, в том же плане:

| Набор навыков | Capability | Как обнаруживается | Команды установки | Для всех остальных harness, откуда |
| --- | --- | --- | --- | --- |
| Matt Pocock Skills | `matt_pocock_skills` | `claude plugin list --json` показывает `mattpocock-skills@…` | `claude plugin install mattpocock-skills@claude-plugins-official --scope user` (официальный marketplace Claude Code, ничего не надо добавлять заранее) | `mattpocock/skills` |
| Ponytail | `ponytail` | `claude plugin list --json` показывает `ponytail@…` | `claude plugin marketplace add DietrichGebert/ponytail --scope user`, затем `claude plugin install ponytail@ponytail --scope user` | `DietrichGebert/ponytail` |

Claude Code спрашивают о его плагинах один раз — и об этих, и о плагине `binnacle`. Плагин, который он уже показывает, из любого marketplace, отмечается как найденный и не трогается. Набор навыков, объявленный `false` в `capabilities`, не предлагается ни Claude Code, ни любому другому harness. Если Claude Code не найден или `claude` нет в `PATH`, никакой плагин не устанавливается, и Summary говорит почему. Манифест, который создаёт init, объявляет `true` для набора, который он установил или нашёл. Соглашения, которые читают Matt Pocock Skills и которые записал бы `/setup-matt-pocock-skills`, init пишет сам, каждое только там, где его нет: `docs/agents/issue-tracker.md` для найденного трекера, с заголовком тикета, `triage-labels.md`, `domain.md` и блок *Agent skills*, который на них ссылается, в `AGENTS.md` или в `CLAUDE.md`, если есть только он (ADR-0042).

Все остальные harness получают оба набора так же, как до них доходят собственные навыки Binnacle (ADR-0039): если `binn` нашёл harness, план выполняет для каждого набора `npx skills add <repository> -g -y --json`, затем `npx skills remove -g -a claude-code [--skip-harness ids] -s <each skill the add installed> -y`, так как у Claude Code остаётся плагин. Удаление называет навыки, которые перечисляет JSON команды add, поэтому план показывает их как заполнитель. Результат add читается по тому, что он установил, а не только по коду выхода: CLI `skills` выходит с ненулевым кодом и считает все навыки неудавшимися, когда не удался один harness, например PromptScript, у которого нет глобальной установки, хотя в остальные он их ставит; поэтому `binn init` тогда спрашивает `npx skills list -g --json`, удаляет из Claude Code навыки набора, которые тот показывает, а Summary называет причину, которую add дал для этого harness. Add, который ничего не установил, записывается как неудачный, его удаление пропускается, и Summary это говорит. Без `npx` в `PATH` команды печатаются вместо выполнения.

### MCP-серверы, которые он регистрирует

После установок, в том же плане, init регистрирует MCP-сервер каждого инструмента в каждом найденном harness, через собственный CLI harness, вне репозитория:

| Сервер | Запускается командой | Уровень |
| --- | --- | --- |
| Serena | `serena start-mcp-server`, с контекстом, который Serena документирует для harness (`claude-code`, `codex`, `vscode`), и `--project-from-cwd` для CLI-harness | пользователь |
| Context7 | `npx -y @upstash/context7-mcp` (нужен `npm`) | пользователь |
| Graphify | `uv run --no-project --with 'graphifyy[mcp]' python -m graphify.serve <project>/graphify-out/graph.json` | только этот проект |

| Harness | Регистрируется через | Сервер Graphify |
| --- | --- | --- |
| Claude Code | `claude mcp add --scope user <name> -- <command>` | `claude mcp add --scope local …`, хранится в `~/.claude.json` для этого проекта |
| Codex | `codex mcp add <name> -- <command>`, в `~/.codex/config.toml` | печатается: Codex не хранит серверов отдельного проекта вне репозитория |
| VS Code | `code --add-mcp '{"name":…,"command":…,"args":[…]}'`, в профиль пользователя | печатается, по той же причине |
| opencode | печатается: его `opencode mcp add` — интерактивный мастер | печатается |

Сервер, уже зарегистрированный в harness, в любом файле, который аудит читает для него (в файле репозитория и в пользовательских файлах Claude Code, Codex и профиля по умолчанию VS Code), отмечается и не трогается. Единственное исключение — Serena, зарегистрированная в пользовательском файле Codex (`~/.codex/config.toml`) с контекстом Claude Code (`--context=claude-code`): план регистрирует её заново с `--context=codex`, и `codex mcp add` записывает это поверх старой записи, только по «да» владельца. Та же запись в `.codex/config.toml` репозитория принадлежит владельцу: она не трогается, а Summary называет её контекст. Harness, чьего CLI нет в `PATH`, получает запись напечатанной, и Summary это говорит. Инструмент, объявленный `false` или оставленный вне плана из-за недостающей предпосылки, не регистрируется; не регистрируется и сервер Graphify без `uv`, даже если `graphify` найден. Init не пишет MCP-записи этих инструментов в репозиторий. Сервер Graphify запускается в собственном окружении с extra `mcp`, поэтому его установка остаётся `graphifyy`.

### Первый граф, который он строит

Последним в том же плане init строит первый граф проекта, чтобы проект выходил из `binn init` уже с ним:

1. `graphify-out/`, выходной каталог Graphify, дописывается в `.gitignore` (или `.gitignore` создаётся с ним) по правилу дописывания ADR-0026, если Git ещё не игнорирует `graphify-out/graph.json`; иначе `.gitignore` не трогается.
2. В корне репозитория запускается `graphify extract . --code-only --allow-dedup-shrink`: извлечение Graphify только по коду, по локальным синтаксическим деревьям, без API-ключа и без вызова модели (ADR-0012). Это та же команда, которую запускает демон. `--allow-dedup-shrink` позволяет Graphify записать граф, который его дедупликация сделала меньше, — иначе он отказывается: граф — пересобираемая проекция (ADR-0036), поэтому меньший граф после слияния ожидаем, а не является потерей.
3. После успешного извлечения `graphify cluster-only . --no-label` строит отчёт Graphify, `graphify-out/GRAPH_REPORT.md`, из которого читается заметка `90-Graphify` в хранилище. Извлечение отчёта не пишет; `--no-label` не даёт Graphify вызывать модель, чтобы назвать сообщества, так что и ему не нужен API-ключ. Демон тоже запускает его после каждого извлечения.

Все три шага входят в план, только если Graphify есть в `PATH` или ставится тем же планом, а `capabilities.graphify` не `false`; Graphify, оставленный вне плана из-за отсутствия `uv`, не получает ни одного. Сборка и отчёт пропускаются, и Summary говорит почему, если к этому моменту Git всё ещё не игнорирует `graphify-out/` или если `graphify` нет в `PATH` — потому что его установка не удалась или положила его в каталог вне `PATH`. Каждый шаг Graphify останавливается по истечении десятиминутного предела демона на один шаг. Неудачная сборка или отчёт попадает в Summary с последней строкой, которую Graphify написал в stderr, а остальной план выполнен; неудачный отчёт сохраняет граф, записанный извлечением; демон построит граф при одном из следующих опросов, когда проект зарегистрирован и `graphify` запускается (*Graphify*, ниже).

## Node / pnpm

Runtime baseline проекта: Node.js 24 LTS. Для управления workspace используйте pnpm.

## Matt Pocock Skills

Назначение: грилинг требований/предметной области, создание долговременного контекста/ADR, написание спек и нарезка тикетов.

Ожидаемый поток проекта:

`grill-with-docs → to-spec → to-tickets`

`binn init` пишет раскладку tracker и документов предметной области, которую читают эти навыки, поэтому `setup-matt-pocock-skills` не нужен.

Не зашивайте детали upstream-реализации в Binnacle; обнаруживайте/настраивайте через адаптер. Единственное исключение — форма файлов соглашений, которые пишет `binn init`: она сохраняется такой, как её пишет `setup-matt-pocock-skills`, чтобы навыки читали их как свои (ADR-0042).

## Ponytail

Назначение: политика кодирования против переусложнения/YAGNI. Держите его как capability политики кодирования, а не как гарантированный оптимизатор токенов.

Рекомендуемое значение по умолчанию: `full`, настраивается на проект/роль.

## Serena

Назначение: семантический поиск/редактирование кода на уровне символов через MCP-инструменты на основе language server.

Binnacle должен проверять, что Serena доступна для поддерживаемых клиентов/проектов, но не должен проксировать все операции Serena.

## Graphify

Назначение: строить граф знаний об архитектуре кода/документов и отвечать на запросы по нему; поддерживать запросы влияния/путей и опциональный экспорт в Obsidian.

Текущее имя upstream-пакета — `graphifyy` (CLI `graphify`). Рекомендуемая установка — `uv tool install graphifyy`, чей graphify (0.9.76 на момент написания) принимает `--allow-dedup-shrink`; graphify, который не знает этого флага, пропускает его, как пропускает любой незнакомый аргумент, поэтому тот, что отказывается от уменьшившегося графа, проваливает этот запуск с причиной graphify, как любой неудачный запуск. Его MCP-серверу нужен extra `mcp`, который регистрация init получает через `uv run --with 'graphifyy[mcp]'`.

Рекомендуемое поведение проекта:

- граф кода полезен для межмодульной архитектуры/анализа влияния;
- `.scratch/**` обычно должен игнорироваться;
- демон держит граф актуальным (ADR-0036): раз в минуту он читает коммит ветки по умолчанию каждого зарегистрированного проекта (`origin/HEAD` или `main`), и когда она ушла дальше последнего запуска, запускает в фоне в зарегистрированном checkout `graphify extract . --code-only --allow-dedup-shrink` — локальные синтаксические деревья, без модели, без сети (ADR-0012), — а после успешного извлечения `graphify cluster-only . --no-label`, который строит `GRAPH_REPORT.md` без модели, называющей сообщества. Неудачный отчёт — неудачный запуск, с причиной, а граф, записанный извлечением, сохраняется. Запуск идёт, только пока этот checkout на ветке по умолчанию, `capabilities.graphify` не `false`, `graphify` есть в PATH демона и Git игнорирует `graphify-out/`; по одному запуску на проект за раз и не больше одного в очереди, так что серия merge стоит двух запусков. Каждый исход записывается как событие, и его читают раздел `graph` в snapshot и его пункты внимания (`docs/03-mcp-and-skills.md`). Неудачный запуск сохраняет последний хороший граф и повторяется при следующем движении ветки по умолчанию, а не каждую минуту;
- экспорт в Obsidian опционален;
- Graphify остаётся заменяемым/опциональным на уровне архитектуры системы.

## Context7

Назначение: получать актуальную документацию внешних библиотек/фреймворков/API для конкретных версий. Его не следует использовать для внутренней бизнес-логики.

У пользователя Context7 уже может быть настроен глобально; init сначала читает файлы harness и регистрирует его только в том harness, где его нет.

## ast-grep

Назначение: синтаксически осознанный структурный поиск/codemods, особенно для больших механических изменений, где regex/текстовый grep небезопасен.

## Obsidian

Назначение: представление Project Brain для человека, ссылки, заметки и canvas/экспорт Graphify.

Obsidian опционален и не должен быть каноническим обязательным хранилищем. `binn init` не устанавливает ни Obsidian, ни хранилище. Хранилище задаётся `obsidian.vaultPath` в файле настроек этой машины, `~/.binnacle/settings.json`, вне любого репозитория; `binn init` предлагает его в своём плане, когда собственный список Obsidian на этой машине содержит ровно одно хранилище, а иначе говорит, как его задать (`05-installation-checklist.ru.md`, *Опционально: Obsidian*).

Проекция хранилища, которую ведёт демон, пишет такую структуру (`05-installation-checklist.ru.md`, *Проекция хранилища*):

```text
Vault/
└── Projects/
    └── <Project>/
        ├── Product/       roadmap, last snapshot, last daily
        ├── Specs/
        ├── Decisions/
        ├── Research/
        └── 90-Graphify/   Graphify's report
```

## OpenTelemetry

Используйте нативную поддержку OTel в coding harness, где она есть. Нормализуйте только то, что действительно сообщается.

## Поддержка провайдеров/harness

Архитектура должна различать:

```text
harness: claude-code | codex | gemini-cli | other
provider: anthropic | openai | zai | google | local | other
model: nullable provider/model identifier
profile: user-defined launch/config profile
```

Это позволяет одному и тому же harness работать с разными провайдерами/профилями.
