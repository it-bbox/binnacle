# 09: The daemon projects the Project Brain into an Obsidian vault

Status: DONE
Triage: ready-for-agent
Blocked by: None
Spec: `docs/specs/project-brain-tools-graphify-obsidian/spec.md`

**What to build:** a one-way projection of each registered project into the owner's Obsidian vault (ADR-0036). The vault path is `obsidian.vaultPath` in a new owner-only per-machine settings file in the Binnacle home, read on every refresh, after the credentials file's pattern (decision 13). When the default branch moves, the daemon renders the project under `Projects/<Project>/`. Specs holds each spec and its tickets, Decisions the ADRs, and Research the project's other Markdown docs. The source is committed `main`, read through the Git adapter, never the working tree. Relative Markdown links between projected files become Obsidian links. Each generated file carries frontmatter naming it generated by Binnacle, with its source path and commit. The daemon writes, rewrites and deletes only files with that marker, so a note the human wrote is never touched. A generated note whose source is gone is removed. Writes are whole-file, through a temporary name and a rename. A vault path that does not exist or cannot be written is the attention item `vault.unwritable`. No setting means no projection and no attention item.

- [x] With the setting pointing at a temporary vault, a commit to the default branch leads to Specs, Decisions and Research notes under `Projects/<Project>/`.
- [x] A relative link between two projected docs is an Obsidian link in the vault.

Only `Specs`, `Decisions` and `Research` (`FOLDERS`) are swept for notes whose source is gone, so ticket 10's Product and `90-Graphify` notes are outside that sweep; ticket 10 writes them through the same `writeNote`, which keeps the marker and symbolic-link rules.
- `docs/roadmap.md` is left out of Research: it is Product's roadmap note, ticket 10's. Obsidian links are vault-relative, `[[Projects/<Project>/<folder>/<note>|label]]`, so ticket 10's roadmap note can link to the specs the same way.
- `graph.ts` now exports `defaultCommit` and `manifestOf`, which the projection shares.

### Decisions taken here

- **When it renders.** Once a poll, a project is rendered when its default branch's commit, or the vault path, differs from what was last rendered in full; a failed render is retried on the next poll. So the first poll after a start renders every project once, and a new setting, or a second vault, takes effect within a poll. A note the human deletes or edits comes back at the next move or start (`ponytail:` in the code).
- **What `vault.unwritable` covers.** A vault path that does not exist, is not a directory or cannot be written, and also a settings file that is not JSON or a `vaultPath` that is not an absolute path: the owner meant to set a vault, and silence would hide it. No file, or no `obsidian.vaultPath`, is no projection and no attention item. It is read when the snapshot is served; a write that fails inside a writable vault is only in the daemon's log (`ponytail:`).
- **The settings file is not refused when others can read it**, unlike the credentials file: it holds a path, not a secret. The docs still say to make it owner-only.
- **The project's folder** is the manifest's `project.name`, or its id, with what a path or an Obsidian link cannot hold replaced by `-`.
- **Specs** project each spec directory's `spec.md` and its `issues/*.md`, flattened to `Specs/<slug>/<NN>-<ticket>.md`, as the spec names them; **Research** keeps the layout under `knowledge.docs`.
- **A source's own frontmatter** is merged with the marker rather than given a second block.
- **No note is written through a folder that links out of the vault**: a symbolic link the human made there is not followed for writes, nor for the sweep.
